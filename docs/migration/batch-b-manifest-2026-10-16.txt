RESOLVED PLAN  (exact hosting contract, evidence and per-object table: plan 8.2.1)
  1. Mechanism: an S3-compatible object store with free egress, serving the four ONNX files
     from one public prefix. Recommended: Cloudflare R2 (zero egress fees). Same-catalogue
     alternatives: Backblaze B2 and Wasabi (both S3-compatible). Supabase Storage is already
     in this stack but its free egress is metered (~5 GB/month).
  2. Layout: the four objects must share one base URL, because inference.ts builds the sidecar
     URL as ${modelUrl}.data. So the bucket holds e.g. <base>/spoter_v2_model.onnx and
     <base>/spoter_v2_model.onnx.data side by side. Object names must stay EXACTLY these -
     the .data suffix is derived, never configured:
       <base>/spoter_v2_model.onnx       <base>/spoter_v2_model.onnx.data
       <base>/spoter_pilot.onnx          <base>/spoter_pilot.onnx.data
  3. Cross-origin and range: the bucket must send Access-Control-Allow-Origin for the
     deployed origin (mirroring the `*` web/vercel.json sets for /spoter_.*), plus
     Access-Control-Expose-Headers: Content-Range, Content-Length, Accept-Ranges, and must
     answer OPTIONS preflights for the Range header. Cache-Control: public,
     max-age=31536000, immutable; Content-Type: application/octet-stream.
     CORRECTED 2026-10-16 by the loopback contract test (docs/migration/
     onnx-hosting-contract-test-2026-10-16.md 6.2 and 6.3): the earlier claim that RANGE/206 SUPPORT
     IS REQUIRED because 'the installed onnxruntime-web issues ranged requests' is NOT supported by
     measurement - with onnxruntime-web 1.30.0 and this explicit externalData configuration the
     library fetched each graph and each whole .data sidecar with plain full GETs and sent no Range
     header at all. Range/206 stays RECOMMENDED (resume/partial reads, future ORT behaviour), not
     required. Likewise a preflight is not sent for every request shape: Chromium safelists a
     single-range Range header and preflighted only the suffix form.
  4. Environment variables (Vite inlines VITE_* at BUILD time, so set them in the Vercel
     project before the build, and in web/.env.local for local work):
       VITE_SPOTER_V2_URL=<base>/spoter_v2_model.onnx
       VITE_SPOTER_PILOT_URL=<base>/spoter_pilot.onnx
       VITE_AVATAR_GLB_URL   leave UNSET - the GLB is committed and served same-origin
  5. Runtime URLs: the app fetches <VITE_SPOTER_V2_URL> and <VITE_SPOTER_V2_URL>.data, and
     the same shape for the pilot pair. NO URL IS INVENTED - <base> is the owner's chosen
     host (a custom domain is recommended; r2.dev URLs are documented as development-only).
  6. Availability to Vercel: the Vercel build needs NOTHING from the host. Vite inlines the
     two VITE_* values at build time and the browser fetches the ONNX pairs directly at
     runtime. The committed GLB is copied from public/ into dist/ and served same-origin at
     /avatar/SignVox_Female_Competition_Prototype.glb.
  7. NOT claimed: deployment readiness. Nothing has been uploaded, no bucket exists, and the
     request, CORS and Range behaviour has not been exercised against a real host.
